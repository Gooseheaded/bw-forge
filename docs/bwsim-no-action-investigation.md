# bwsim no-action replay investigation

Scope: only the three corpus replays that load and advance under bwsim while
producing no gameplay effects. No production, reducer, or vendored runtime code
was changed during this investigation.

## Result

This is a **replay-conversion compatibility bug**. The raw replays contain
normal actions, and `bw_rep_to_drpl` preserves every action byte-for-byte, but
the affected remastered action streams refer to units in a UnitId namespace
that is `0x1EA4` below the UnitIds created by bwsim for the same initial units.
The converted DRPL therefore is not executable against the state it loads.

`bw_load` succeeds, frames advance, and action counters increase. However, the
first `Select` (`0x63`) commands resolve no units. Later orders, training, and
build commands then run with an empty selection and have no gameplay effect.

“Exact” compares frame, mapped owner, opcode, and command payload for every
action. Thus actions do not disappear from the raw REP or DRPL and are not
stuck in scheduling. They disappear semantically when bwsim resolves the first
remastered 32-bit unit references.

Storm-player to owner mapping is correct: action counters accrue to the intended
owners, and `pvt_mid` uses identity mapping yet fails identically. Controller or
player mapping is not the cause.

The same relation holds in the other failures. For example, the first Terran
building IDs are `0x0D9A → 0x2C3E` in `zvt_mid` and `0x0E15 → 0x2CB9` in
`tvz_mid`, each exactly `+0x1EA4`.

The affected streams use remastered 32-bit-UnitId opcodes:

- `0x60`: default order with a 32-bit target ID
- `0x61`: explicit order with a 32-bit target ID
- `0x63`: select with 32-bit IDs
- `0x64`: shift-select with 32-bit IDs
- `0x65`: deselect with 32-bit IDs

## Proof-of-fix experiment

Without changing production files, a temporary DRPL-only experiment added
`0x1EA4` to every nonzero UnitId field in those five opcodes. This changes no
frames, owners, opcodes, or non-UnitId payload data.

At frame 1,000 the unmodified simulations still had four workers per human and
initial resources. The normalized simulations had active economies and unit
production:

| Fixture | Frame-1,000 normalized state |
|---|---|
| `zvt_mid` | owners 0/3: 5/5 workers, 84/60 minerals |
| `tvz_mid` | owners 0/1: 5/5 workers, 60/76 minerals |
| `pvt_mid` | owners 0/1: 7/6 workers, 26/42 minerals |

All three normalized DRPLs reached their header terminal frame. Two complete
reruns of each produced identical final player records, live-unit count, and
HUD-unit byte hash. This proves both the cause and the required UnitId mapping.

This experiment was not installed as a production fix, so downstream
ShieldBattery comparisons have not yet been rerun. The earlier empty-build-order
differences therefore remain until an upstream release is made and vendored.

## Minimal fix and ownership

The smallest correct fix is in upstream **headless-bwsim's replay-conversion /
execution compatibility boundary**, not BW Forge:

1. Recognize the affected low remastered UnitId-tag family.
2. Translate every nonzero 32-bit UnitId field in opcodes `0x60`, `0x61`,
   `0x63`, `0x64`, and `0x65` by `+0x1EA4` before the DRPL is executed (or make
   the engine's SCR UnitId resolver perform the equivalent mapping).
3. Guard the mapping using conversion knowledge of the replay's UnitId family;
   do not blindly shift working direct-ID streams.
4. Add all three files as regression cases: actions must affect state, terminal
   reruns must be deterministic, and the working direct-ID replay must remain
   unchanged.

After that fix is tested and released upstream, BW Forge should refresh its
pinned vendored copy and rerun the three normal end-to-end comparisons. A local
BW Forge adapter patch or direct edit to `third_party/bwsim` would create the
forbidden hidden fork and is not recommended.

## Direct answers

1. **Exact disappearance stage:** the converted DRPL retains and schedules the
   actions, but its first SCR 32-bit UnitIds do not resolve against bwsim's
   loaded unit namespace; selections are empty and dependent actions are no-ops.
2. **Common factor:** all three use the low remastered UnitId-tag family whose
   IDs require `+0x1EA4`; all are build-13,515 remastered files and have the
   correlating, non-causal GCFG trailer value 4.
3. **Classification:** **REPLAY-CONVERSION BUG**. The converter emits an action
   stream that is byte-faithful to REP but incompatible with the state bwsim
   loads. It is not a BW Forge host/load-sequence bug.
4. **Smallest fix:** normalize the five SCR 32-bit UnitId-bearing opcode fields,
   guarded to the affected tag family.
5. **Ownership:** upstream headless-bwsim; then release and refresh BW Forge's
   vendor pin.
6. **Execution after normalization:** yes. All three perform mining/production,
   reach their terminal frame, and rerun deterministically.
7. **Downstream mismatches:** not yet classified after the fix because no
   upstream production artifact exists. The existing 678 missing build-order
   events are still present in the unmodified backend; rerunning downstream is
   the required acceptance step after the upstream release.
